# 分支、版本与同步

## 唯一稳定入口

- GitHub 默认分支：`master`。不另建 `main`、`develop` 或长期版本分支。
- 新任务：从最新 `origin/master` 建立短期 `codex/*` 分支，PR 直接指向 `master`。
- 合并前检查最终提交的 CI 与阻塞性审查，沿用仓库现有的 squash 合并方式；历史整合关系由本地 bundle、整合提交与 PR diff 留证，不修改仓库合并策略。
- 发布：版本文件、应用、Worker、页面、备份清单和文档一致；Tag 与 Release 通过项目现有发布门禁后再创建。

## 为什么过去不同步

2026-09-10 核对时，远端 `master` 为 2.1.0，现有本地运行基线为 2.2.0，公开 Release 为 v2.0.0。部分 PR 以功能分支为目标，导致功能已经用于本机，却没有进入默认分支。

2.3.0 以既有运行提交 `c650128` 为整合基础。现有离线转写、内容复盘、周总结、动态排期与 AI 恢复修复进入同一条主干；其他实验和未完成工作必须另行验证，不因“收缩分支”而自动合并。

PR #86 已合并，v2.3.0 已发布并部署。本地分支 74 → 37、GitHub 分支 69 → 41；仅清理有覆盖证据且无依赖的分支。剩余分支与 PR 仍需逐项核对。最新交付边界见 [项目当前进度](../PROJECT_STATUS.md)。

文档提交可正常合并到 master；仅文档变动无需重启运行服务，也不重打 v2.3.0 Tag。业务代码升级仍须执行实际部署验收。

## 日常流程

工作区干净、没有本地独有提交时：

```powershell
git fetch origin --prune
git switch master
git pull --ff-only
git switch -c codex/your-task
```

有未提交修改时先停止切换，确认修改用途并保存。正式运行目录由服务管理器决定，不能因为另一个目录完成 `git pull` 就认为已经部署。

完成后只暂存本次文件，提交、普通 push，创建目标为 `master` 的 PR。检查通过并合并后，在实际运行目录按现有部署流程升级、重启和验收。真实 AI 调用、任务重跑和真实投稿不用于常规版本验收。

## 历史分支清理标准

1. 清理前保存全部引用清单、工作目录清单与可通过 `git bundle verify` 的完整 Git bundle。
2. 分支提交已经被 `master` 包含，或由已合并整合 PR 的基线祖先与最终 diff 证明等价覆盖；且没有开放 PR 以该分支为来源或目标。
3. 分支没有被工作目录占用。活动服务目录、未提交修改与唯一未合并提交一律保留。
4. 核对远端实际分支 SHA 后再删除引用；不强推、不删除目录、不重写历史。
5. squash 合并后的分支需要单独检查补丁等价关系，不能仅凭 PR 标题或关闭状态删除。

备份保存在本地 Git 元数据目录，不上传 GitHub；它保存提交历史，不代替数据库、配置或未提交文件备份。恢复某个已删除分支时，先从引用清单找到 SHA，然后运行 `git branch <原分支名> <SHA>`；对象缺失时从 bundle 获取。

工作目录本身不是分支。保留工作目录不会影响 GitHub 首页；带本地修改或运行环境的目录不能仅为减少数量而删除。

## 版本口径

- `VERSION`：当前代码版本，本次为 2.3.0。
- GitHub 默认分支：已经合并的代码入口。
- Tag / Release：通过最终版本门禁的发布快照；不移动旧 Tag。
- 本机运行版本：必须核对实际服务目录、Git 提交、API / Worker 版本与页面显示。

历史开发日志记录当时状态，不能作为当前部署结论；以日志顶部的最新整合验收记录为准。
